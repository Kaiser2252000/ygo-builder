## Epic Summary

Epic 1 established the card discovery foundation for the deck builder. Story 1.1 delivered backend card search, frontend search state, search UI states, response envelopes, and backend pytest coverage. Story 1.2 delivered card image resolution, `imageUrl` in card API payloads, CardInfo context, hover and keyboard-focus preview behavior, and the Card Info panel.

Planned stories:

- Story 1.1: Search Cards by Name or Description - done
- Story 1.2: View Card Details and Image on Hover - done

Validation completed during the epic:

- `python -m pytest` passed
- `npm run build` passed
- `npm run lint` passed

## What Went Well

- The project scaffold became usable quickly enough to support both backend and frontend feature work.
- Backend card search followed the required `{data, error}` envelope and gained route/service tests early.
- Code review caught real issues before closure: stale async search results, missing backend diagnostics, inefficient image lookup, and hover-only card preview.
- The Story 1.2 image lookup moved from per-card directory scans to an in-memory filename index, which is the right shape for search result rendering.
- The CardInfo interaction was expanded beyond mouse hover to keyboard focus and blur, improving accessibility before the deck-builder UI depends on the same pattern.

## Challenges

- Frontend component behavior remains under-tested because the frontend package has no `test` script or Vitest/Testing Library harness.
- Story 1.1 created much of the application scaffold, so validation had to cover both feature behavior and project setup.
- Card data has a backend Python field conflict around `def`, requiring explicit serialization to preserve the API contract.
- The Epic 1 description lists FR3, but the actual add-to-deck interaction is planned in Story 2.4 under Epic 2. Epic 1 is complete by its two sprint-tracked stories, while FR3 remains intentionally deferred to the deck interaction story.

## Review Feedback Patterns

- Async UI state needs defensive handling. Story 1.1 required stale response protection so older searches cannot overwrite newer results.
- Backend failures need diagnostics, even when the client receives a clean envelope.
- Repeated lookup work needs attention before it lands in user-facing loops. Story 1.2's image lookup initially scanned the image directory per card.
- Interaction requirements should include keyboard behavior when hover is used for information display.

## Key Lessons

1. Treat every cross-panel interaction as both mouse and keyboard behavior from the story spec onward.
2. Search-result payload work can amplify backend costs quickly; cache or index filesystem-derived data before wiring it into result lists.
3. The project needs frontend test infrastructure before more state-heavy UI lands in Epic 2.
4. Sprint status is the source of truth for epic closure, but requirements coverage should still be checked for cross-epic items like FR3.

## Next Epic Preview

Epic 2 introduces Deck Management: deck CRUD backend, deck library UI, deck builder zones, drag-and-drop and right-click card management, sorting, clearing, saving, cover upload, import, and export.

Epic 1 creates useful foundations for Epic 2:

- `Card` data shape is available for deck slots and deck interactions.
- `SearchContext` and `CardInfoContext` provide the cross-panel state patterns Epic 2 will reuse.
- Card image URLs are already resolved through the backend and can be reused by deck slots or library previews if needed.
- The accessibility fix for search results should become the standard for deck slots and actionable deck rows.

## Risks For Epic 2

- Deck features will add more shared state, making the missing frontend test harness more expensive if left unresolved.
- Story 2.4 depends on the gap between Epic 1's FR3 wording and Epic 2's actual drag/right-click implementation. Keep FR3 explicitly attached to Story 2.4 during story creation and review.
- File-backed deck persistence needs careful validation and error envelopes to match the pattern established by cards.
